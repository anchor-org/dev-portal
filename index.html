Anchor API (1.0.0)

Download OpenAPI specification:

Anchor has no custom backend server — the client talks directly to Supabase. Every endpoint below is the auto-generated Supabase PostgREST REST API:

  • RPC endpoints (POST /rpc/{function_name}) wrap the public.* SQL functions defined in supabase-sql/*.sql. This is almost all of the write surface and most reads — business logic lives in Postgres, not in the app.
  • Table endpoints (GET/PATCH /{table}) are PostgREST's automatic REST mapping over a handful of tables the client queries directly instead of through an RPC. Every table has Row Level Security enabled; what a request can see or change depends on the caller's JWT, not on anything this spec enforces.
  • Auth endpoints (/auth/v1/*) are Supabase's standard GoTrue service, used unmodified (sign up, sign in, sign out, session refresh). They're listed for completeness but not fully modeled here — see https://supabase.com/docs/reference/javascript/auth-api.
Expo SDK 54 docs (client-side reference, not part of this API)

Known drift between SQL source and live schema

supabase-sql/ is a folder of one-shot scripts pasted into the Supabase SQL Editor by hand — there is no migration history, so two functions changed shape more than once across separate files:

  • get_my_challenges: supabase-sql/close-challenge.sql added a status column; supabase-sql/today-grouped.sql separately drop-and-recreated the same function adding member_count (dropping status in the process, since DROP FUNCTION + CREATE FUNCTION resets the column list each time). The TypeScript client (lib/challenges.ts) reads both status and member_count, so the function actually deployed today must return both — neither SQL file alone matches production. Confirm the live signature with \df public.get_my_challenges before trusting this spec's schema.
  • get_challenge_members_summary: same pattern — the version in supabase-sql/challenge-members-summary.sql returns only (user_id, display_name); supabase-sql/challenge-settings.sql drop-and-recreates it adding role. The client reads role, so the three-column version is what's documented here, but re-verify live.

This spec otherwise documents each function's final shape (the last file to define it, cross-checked against what lib/*.ts actually reads off the response).
